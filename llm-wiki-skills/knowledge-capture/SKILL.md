# knowledge-capture — 把值得留的分析落盘

职责单一：**判断这次分析值不值得沉淀，值得就按模板写进 `wiki/analysis/` 并更新清单。**

## 先判断值不值得（判定点 F）

三条**全部满足**才沉淀：

1. **跨 ≥2 个概念页** —— 单页复述不值得留，那一页本身就是答案
2. **含推理链** —— 有「从 A 推到 B 再推到 C」的过程，不是直接给结论
3. **以后可能再问** —— 一次性事实（今天几号、这个接口返回什么）不入库

**不满足就不沉淀，直接结束。** 沉淀库不是聊天记录。

## 一条容易判错的边界

**「重要」不等于「值得沉淀」。**

- 「Kafka 靠页缓存和零拷贝实现高吞吐」→ 这是 [[Kafka]] 概念页里已有的内容，**不沉淀**，重复
- 「Kafka 这套设计能不能借鉴到我们的日志采集系统」→ 跨概念 + 有推理 + 会再问，**沉淀**

判据只有一条：**这个分析里有没有概念页没写过的东西？**

## 写的时候

1. 套 `wiki/_templates/digest-template.md`，文件名 `<日期>-<问题概括>.md`
2. 存入 `wiki/analysis/`
3. 回 `wiki/analysis/digest-index.md` 加一行

## 七段都要写，其中两段不能省

| 段 | 写法要求 |
|---|---|
| 问题是什么 | **保留用户的原话口语**，不要改写成书面语——下次是拿这句做语义匹配的 |
| 怎样理解问题 | 拆层面、列出涉及概念、指出容易和什么混淆 |
| 结论 | 2–4 句，直接给答案，不复述过程 |
| **推理链** | **不能省**。逐步写：从哪个前提出发、经过哪几步、在哪一步转折 |
| 依据 | 挂 `[[页面]]`，能点回去 |
| **边界** | **不能省**。什么范围内成立？什么情况不适用？ |
| 下次怎么做得更好 | 这次哪里偷懒了、下次该先看哪页 |

**推理链和边界是这页全部价值所在。** 只有结论没有路径的沉淀，下次还得重推一遍，等于没做；没有边界的结论会被误用到不该用的地方。

## 更新索引时的写法

```markdown
- [[2026-11-06-Kafka的高吞吐设计能不能借鉴]] — Kafka 为什么这么快、页缓存和零拷贝能不能用在自己系统、
  什么情况下这套优化失效。结论：两个都是通用手段，但有硬前提——数据不需应用层加工、有可靠性兜底。
```

**一条描述要写两半，缺一半就废：**

| 前半：用户会怎么问 | 后半：结论是什么 |
|---|---|
| 用提问的口语，带上同义说法 | 一两句直接给答案 |
| 「Kafka 为什么这么快 / 能不能用在我系统 / 什么情况下失效」 | 「两个都是通用手段，但有硬前提」 |

**只写结论会怎样**：用户说「Kafka 为什么快」，描述里只有「页缓存」「零拷贝」，语义匹配不上，这条沉淀等于不存在。
**只写问题会怎样**：命中了还得点进去才知道答案，白跑一趟。

> 这条是实测出来的：6 条沉淀页一开始只写了结论，命中率 2/6；改成「问题 + 结论」双半结构后升到 **5/6**。

## 写描述时的一个反直觉点

**别写得像论文标题。**

- ❌ 「关于分层与建模关系的思考」—— 没有一个可匹配的锚点
- ✅ 「分层和建模是不是一回事、该先做哪个。结论：两者正交」

标题式写法看起来整齐，但它丢掉的全是检索时要用的词。

## 同类问题怎么办

**更新旧页，不新建。**

比如已经有一篇「分层与建模的关系」，后来又想到「在 Inmon 路线下这个结论不成立」——应该追加到旧页的「边界」段，而不是新建一篇「再论分层与建模的关系」。

沉淀库一旦允许同类多篇，很快就变成一堆互相矛盾的答案。

## 三条禁令

| 禁止 | 原因 |
|---|---|
| 把聊天记录式的内容沉淀 | 沉淀库是结论库，不是对话存档 |
| 只写结论不写推理链 | 下次无法验证，只能重推 |
| 不写边界 | 结论会被用到不适用的场景，且看不出错 |
